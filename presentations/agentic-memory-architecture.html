01

Executive Summary

We've built a shared memory system for AI agents that lets them learn from each other's sessions, share precedent across workflows, and maintain that knowledge automatically. The system is in use locally on two workflows (core platform development and Salesforce development), where we're dogfooding it to prove out the architecture and fine-tune the real-world experience. The overall design has been pressure-tested against 18+ external sources from academia and industry, though the current implementation doesn't yet address all of the findings.

The architecture decomposes into three layers: Memory (storage), Learning (extraction and maintenance), and Personalization (serving the right knowledge to the right agent). We operate at Level 4 (agentic learning and memory) locally today. Level 5 (Alexandria: the org-wide knowledge library) is an aspirational vision that would require organizational buy-in and investment to pursue.

This document focuses on the architecture: how it works, step-by-step processes, honest challenges, and the vision for what it could become. For the business case and landscape context, see the companion decks (Alexandria pitch book and Memory, Context & Graphs landscape primer).

Architecture: Memory / Learning / Personalization

The architecture spans three layers with explicit boundaries between them. Failures concentrate at those boundaries: conflating a retrieval problem (Personalization) with a storage problem (Memory) or an extraction problem (Learning) is the most common design mistake in agent memory systems.

M/L/P Architecture with layer boundaries

    tb["Token budgets"]
    pd["Progressive disclosure"]

  subgraph L["Learning — Async extraction"]
    direction LR
    refl["Session-end reflection"]
    dp["Digestive pipeline"]
    cond["Condensation"]

    refl --- dp --- cond --- forg

  subgraph M["Memory — Storage infrastructure"]
    direction LR
    les["Lessons DB"]
    conn["Connections"]
    ent["Entities"]
    sp["Scratchpads"]
    les --- conn --- ent --- sp

  P -->|"Usage signals + outcomes"| M
  M -->|"Raw material"| L
  L -->|"Structured knowledge"| P

Key architectural distinction: Each layer has different failure modes and maintenance rhythms. A Memory failure is data loss. A Learning failure is a missed insight or false lesson. A Personalization failure is serving the wrong context. Separating them prevents misdiagnosis. The memory layer is an active participant in its own maintenance (agentic memory), not a passive store.

The Learning Loop (Step-by-Step)

Every agent session follows the same lifecycle. The loop is the same whether the agent is working on a core platform ticket or a Salesforce development task.

Agent session lifecycle
sequenceDiagram
    participant Agent
    participant API as HTTP API
    participant Store as Learning Store
    participant Pipeline as Digestive Pipeline

    Agent->>API: POST /sessions (register)
    API-->>Agent: Session ID + scratchpad

    Agent->>API: GET /sessions/{id}/context
    API->>Store: Query lessons, precedent (workflow-scoped)
    Store-->>API: Relevant lessons + decision traces
    API-->>Agent: Context payload (token-budgeted)

    Note over Agent: Agent works (skills, tools, code)
    Note over Agent: Updates scratchpad every 3-5 actions

    Agent->>API: DELETE /sessions/{id} (end session)
    Note over Agent: Includes: summary, reflection,
lessons, decision traces

    API->>Store: Write lessons + traces (scoped)
    API->>Pipeline: Queue digestive processing
    Pipeline->>Store: Reduce → Reflect → Reweave → Verify → Archive
    Note over Store: Next getContext returns
these lessons
  1. Register session. Agent identifies itself, declares what it's working on. System creates or loads a scratchpad (per-task state).
  2. Load context (getContext). System retrieves relevant lessons and precedent, scoped by workflow and task similarity, within a token budget. Optionally includes Alexandria index and rendered claims.
  3. Do the work. Agent uses skills, tools, and files. Updates scratchpad with state, decisions, and progress.
  4. End session with reflection. Agent submits: summary of what was done, structured reflection (what was learned, what to watch for), and optionally guardrail suggestions, knowledge capture, or warnings for future sessions.
  5. System writes and digests. Lessons and decision traces are stored (workflow-scoped). The digestive pipeline processes them asynchronously: extracting atomic claims, finding connections, updating existing knowledge, validating, and archiving source material.
  6. Next session benefits. The next agent's getContext returns these lessons. The loop compounds.

The Digestive Pipeline

Raw knowledge entering the system is not yet useful. It is food, not capability. The digestive pipeline transforms it. Each phase runs in isolation with fresh context to prevent contamination between steps.

Five-phase digestive pipeline
flowchart LR
    R["Reduce
Raw → atomic claims"]
    RE["Reflect
Find connections"]
    RW["Reweave
Update existing"]
    V["Verify
Schema + dedup"]
    A["Archive
Mark processed"]
    R --> RE --> RW --> V --> A
Phase What it does Analogy
Reduce Extract atomic claims from source material. A 2000-word battlecard yields five entity-anchored claims. The rest is discarded. Digestion: break down bulk into building blocks.
Reflect Find connections. Where does each new claim link to what already exists? Connections make both claims more retrievable. Cross-referencing: linking new knowledge to existing understanding.
Reweave Backward maintenance. "If this existing claim were written today, knowing what we now know, what would be different?" New material strengthens existing structures. Revision: the graph gets stronger claims, not just more claims.
Verify Immune system. Schema validation, retrieval filter quality check, entity resolution, duplicate detection. Malformed claims never enter the graph. Type checker: correctness checks on installed software.
Archive Processed source material exits the active workspace. What remains is extracted value: clean, connected, integrated. Waste removal: keep the nutrients, release the bulk.

Layered scope

Retrieval spans four layers, from narrow to broad:

LayerScope
ProjectThis task, this ticket
Team / domainShared best practices
FrameworkCross-workflow lessons
OrganizationEntity graph, org-wide

Berrypicking

Retrieval isn't always one-shot. The system can do multiple passes: an initial pass finds relevant lessons, the retrieval logic reassesses ("given what I found, what else do I need?"), and runs another pass with a refined query.

This mirrors how people actually look things up. The search evolves as understanding grows.

Claims are installed capabilities. When an agent loads a knowledge claim, it gains a capability it didn't have before. A claim about competitive positioning enables the agent to reason about strategy. A vague claim is a buggy function. A stale claim is a regression. Quality gates are correctness checks on installed software, not tidiness conventions.

Honest Challenges

We pressure-tested the architecture against 18+ external sources across 6+ sessions. Five validated strengths. Seven critical gaps.

Validated strengths (protect these)

Propositional framing ("Since [[X]], therefore Y"): no evaluated system has an equivalent.
Memory evolution (decay, condensation, supersession): ahead of the field; most systems implement only formation and retrieval.
Forgetting design: the most complete in any source evaluated.
3D hierarchical token-level memory: placed at the apex of the 2026 academic survey's taxonomy.
Session lifecycle + scratchpad: independently validated by Anthropic, MAPLE, and the academic survey.

Critical gaps (honest assessment)

Gap Impact Status
Episodic memory (case-based records) Can't retrieve "what happened last time we tried this?" Only abstract lessons, not concrete episodes. Designed
Context pressure for long-running agents Session-boundary model breaks at 1+ hour sessions. We have a CLAUDE.md rule; we need architecture. Planned
Memory integrity and trust model No content trust tiers. No read-time validation. No write-event audit log sufficient for rollback. Defenses are write-time schema/format correctness only. ADR written
Security / blast radius of poisoned claims Alexandria's propositional framing means a poisoned claim is reasoned from, not just referenced. Higher epistemic authority means higher blast radius. Three attack vectors identified: direct lesson injection, reflection poisoning via compromised sessions, and digestive pipeline injection from external sources. Mitigations (trust tiers, audit log, read-time integrity checks) designed but not yet implemented. Designed
Knowledge engineering discipline We recognize "claims are installed capabilities" but haven't built the full engineering practices: dependency tracking, impact analysis, confidence-visible rendering, deprecation management. Planned
Conflict resolution (clash) When getContext returns contradictory lessons, no resolution logic. Agent receives contradictory signals with no guidance. Planned
Event-triggered learning Critical failures wait for session-end batch. Same mistake can recur before the next reflection. Designed
No quantitative benchmarks Can't quantitatively prove "memory helps" or "graph beats filesystem." Letta scores 74% on LoCoMo with a plain filesystem. Research

The benchmarking reality: For simple retrieval, the mechanism doesn't matter. Agents search well with any tool. Our graph's value is not faster retrieval. It is discovery (connections not sought), reasoning (propositional claims as installed capabilities), evolution (forgetting at scale), and governance (trust tiers). These don't show up on standard benchmarks. They show up in enterprise, multi-agent, cross-domain scenarios. We need to build evaluation methods that test what we're actually good at.

Architecture Vision

The vision (pending organizational buy-in) is federated memory with two tiers and a governed bridge. Local developers keep their lightweight, file-based memory that works for them. The organizational tier would provide the shared, governed knowledge graph. Quality gates apply at the promotion boundary, not at local writes.

The federated principle

The filesystem-vs-graph divide is not either/or. Individual developers use lightweight, file-based memory (markdown in a workspace, git-backed). Organizations need governed, cross-domain knowledge. The architecture serves both without forcing one onto the other.

Local tier

.md files in workspace, git-backed, personal/team scope. Slash commands (/note, /remember). Low ceremony, high velocity. No quality gates at local writes.

Organizational tier

Alexandria knowledge graph. Cross-domain, propositional, governed, forgetting-enabled. Claims become installed capabilities.

Bidirectional bridge

Local projects query Alexandria for best practices and precedent. Local learnings promote to Alexandria when they have organizational value. Quality gates apply at the promotion boundary.

The Knowledge Interchange Layer

Any team publishes knowledge into the graph through one contract: {entity, claim, source, confidence, timestamp, author}. Teams don't change their tools. Users post and query from Slack. Customer engagement is actively managed in SFDC. Gemini transcripts get parsed. Each team moves at their own pace. The framework grows by accretion, not revolution.

Phase Goal Key deliverables
1. Core Quality & Safety Close the most dangerous gap (memory integrity) and implement highest-value improvements. Decay tiers + RetentionConfig. Trust tiers + audit log. Event-triggered learning. Contribution quality gates. Read-before-write discipline.
2. Episodic Memory & Context Pressure Close the two structural gaps identified across multiple independent sources. Episodic memory store (exemplars linked to lessons). Context pressure events for long-running agents. Conflict resolution layer. Sub-agent memory hierarchy.
3. Intelligence & Quality Deepen memory quality, provenance, and the learning loop. Quality scoring on claims. Memory strengthening (not just forgetting). Offline consolidation cycle. Source provenance. Confidence-visible rendering in Alexandria.
4. Infrastructure Evolution Architectural changes that enable the next level of capability. Entity and event node types. Skills-as-memory-tier. Claim journal + versioning. Living Memory as a Service (federated memory).
5. Knowledge Engineering Build the engineering discipline that "claims are installed capabilities" demands. Dependency tracking. Blast radius queries. Active deprecation notices. Evaluation framework. Memory explainability.

The strategic opportunity: The industry is converging on graphs, agents, learning loops, and forgetting. No one in the evaluated landscape is building the full knowledge engineering discipline (Phase 5): dependency tracking, impact analysis, capability testing, deprecation management for knowledge claims. If the organization chooses to invest here, it moves from a novel framing to a novel discipline, genuinely unprecedented and difficult to replicate.
